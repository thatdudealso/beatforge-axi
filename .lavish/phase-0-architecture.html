Phase 0 / Architecture Review / 2026-07-16

One music core. Two precise front doors.

BeatForge is a local-first music operation layer with an AXI CLI for agents and CueLab as its human deck. The design keeps model adapters replaceable, treats long inference as durable jobs, and makes command-to-control symmetry testable.

01 / Decision

System shape

Keep deployment local and simple, but preserve hard boundaries. A Python application core owns operations, jobs, audio assets, and adapters. Typer and FastAPI are thin ports over that core. React never shells out and never imports engine knowledge.

flowchart TD Agent["Agent or shell"] --> CLI["beatforge-axi CLI\nTyper + TOON boundary"] Human["CueLab React deck"] --> API["beatforge serve\nloopback HTTP + SSE"] CLI --> App["Application operations\ngenerate / repaint / remix / stems / analyze"] API --> App App --> Jobs["Durable job coordinator\nSQLite metadata + artifact store"] Jobs --> Registry["Engine registry + capability gate"] Registry --> ACE["ACE-Step 1.5 adapter\ndefault"] Registry --> YUE["YuE adapter\noptional vocals"] Registry --> Compat["MusicGen adapter\nconfigurable checkpoint"] Jobs --> Audio["Shared audio pipeline\nFFmpeg + deterministic analysis"] Audio --> MP3["Normalized loop-safe MP3"]
A

Shared operation core

CLI and API call the same typed use cases. This prevents UI-only behavior and keeps output semantics consistent.

B

Local job runtime

GPU work is serialized by default, cancelable, resumable where the engine permits, and observable through terse progress events.

C

Capability-driven UX

Support is declared per loaded model, not guessed from engine name. Unsupported controls are disabled with a reason and CLI calls return a structured error.

02 / Evidence

Engine gate

The initial candidate list contains a licensing conflict. Code license alone is insufficient because local generation requires model weights. The repository will enforce the stricter project rule at registration time.

Model-specific capabilities

ACE-Step turbo supports the editing loop, while base models are required for stem extraction. The registry records model variant, device, precision, and exact capability flags.

MusicGen stays in the project

The adapter, configuration schema, contract tests, and documentation all ship. Activation requires an explicit checkpoint, immutable digest, provenance URL, and machine-readable license. The MIT/Apache allowlist rejects Meta's released weights without removing MusicGen support.

engines:
  musicgen:
    enabled: false
    checkpoint: null
    checkpoint_sha256: null
    provenance_url: null
    model_license: null

Version volatility

The prompt references the older ACE-Step repository and commands. Build against the official ACE-Step-1.5 repository, pin a commit, and isolate its API behind the adapter.

Valid path 1

Train MusicGen-compatible weights from scratch on appropriately licensed data, then publish those weights under MIT or Apache 2.0 with provenance.

Valid path 2

Configure a third-party compatible checkpoint only after its own license and every inherited base weight are verified as MIT or Apache 2.0. No such checkpoint is assumed today.

Not a workaround

User-side download, a separate optional flag, or relabeling the adapter does not change the CC BY-NC license. Those approaches would still violate the stated project policy.

03 / Contract

Adapter interface

Every adapter implements the same five operations. Capability metadata is authoritative, all requests and results are engine-neutral, and engine exceptions are translated before crossing the application boundary.

Python protocol

class MusicEngine(Protocol):
    def descriptor(self) -> EngineDescriptor: ...
    async def generate(self, request, context) -> OperationResult: ...
    async def repaint(self, request, context) -> OperationResult: ...
    async def remix(self, request, context) -> OperationResult: ...
    async def stems(self, request, context) -> OperationResult: ...
    async def analyze(self, request, context) -> OperationResult: ...

Stable contract rules

descriptorEngine, model, license, readiness, device, and per-operation capabilities.
requestValidated paths, time ranges, prompt, duration, seed, format, and operation options.
contextWorkspace, cancellation, progress sink, artifact store, and shared audio tools.
resultArtifacts, normalized metadata, warnings, timing, provenance, and loop facts.
failureStable code, terse message, actionable help, and no raw backend stack on stdout.
capabilities:
  generate: true
  repaint: true
  remix: true
  stems: false
  analyze: true
help[1]: Switch to an ACE-Step base model to enable stems
04 / Surface

CLI and UI symmetry

An operation manifest is the single source of truth for command names, required inputs, capability gates, API routes, and CueLab controls. CI fails when any row loses either front door.

OperationAXI commandLocal APICueLab control
Generategenerate --prompt --duration --outPOST /v1/jobs/generatePrompt, preset, duration, Generate
Repaintrepaint --in --section --promptPOST /v1/jobs/repaintWaveform region plus prompt
Remixremix --in --stylePOST /v1/jobs/remixStyle and source strength
Stemsstems --in --out-dirPOST /v1/jobs/stemsStem mixer and export menu
Analyzeanalyze --filePOST /v1/jobs/analyzeBPM, key, duration, loop facts

AXI output

TOON is serialized only at stdout. Default rows stay at 3 to 4 fields. --fields adds fields, while --full only expands truncated detail. Progress stays on stderr.

job:
  id: j_01J...
  operation: generate
  status: completed
artifact:
  path: track.mp3
  duration_s: 60

Boundary behavior

beatforge-axi serve binds to loopback, owns the engine process, exposes job events over SSE, and serves the production CueLab bundle. The browser never runs arbitrary commands or receives filesystem access beyond explicit import/export endpoints.

07 / Decisions

Confirm before scaffold

The code structure is resolved. Two repository operations remain intentionally unexecuted because they affect external state or the dotfiles installation layout.

Where should the operational firstmate clone live?

The dotfiles-managed vendor snapshot is not a runnable clone. The dotfiles design document recommends editable upstream checkouts under ~/src/kunchenguid, while your prompt asks that installations use dotfiles/dotfiles.

Should Phase 0 create the public GitHub origin now?

An origin lets repo-bootstrap initialize no-mistakes and gives firstmate a normal isolated-worktree workflow. Creating a public repository is an external state change, so it needs explicit confirmation.
